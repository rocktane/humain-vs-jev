# Contrat TypeSafe vérifié le 30 octobre 2026

Lecture des sources officielles, sans clé et sans appel payant :

- [Annonce Jev 1.14](https://typesafe.ai/blog/jev-1-14) : images expérimentales, activées explicitement ; l’annonce historique distingue stable et preview.
- [Images](https://docs.typesafe.ai/images) : assets référencés, formats, limites et activation.
- [Noul](https://docs.typesafe.ai/primitives/noul) : question oui/non, estimation de « oui » dans `answers.<id>.noul`, sans champ `confidence` séparé.
- [API](https://docs.typesafe.ai/api) : endpoint et authentification.
- [Modèles](https://docs.typesafe.ai/models) : état actuel, prioritaire sur les alias décrits dans l’annonce historique.

## Requête retenue

`POST https://api.typesafe.ai/v1/systemone`

Headers : `Authorization: Bearer <clé>`, `Content-Type: application/json`, `TypeSafe-Danger-Zone-Images: true`.

```json
{
  "model": "jev-1.14.0",
  "state": {"image": "REFERENCE_OPAQUE_UNIQUE"},
  "assets": {
    "REFERENCE_OPAQUE_UNIQUE": {
      "type": "image",
      "format": "jpg",
      "data_base64": "BASE64_DES_OCTETS_JPEG"
    }
  },
  "questions": {
    "generated": {
      "type": "noul",
      "instructions": "Is this image generated by artificial intelligence?"
    }
  }
}
```

L’identifiant d’asset est renouvelé pour chaque requête. Aucun nom de fichier, provenance, vérité terrain, autre image ou choix humain. Les deux requêtes utilisent les mêmes instructions. Aucun SDK Go supposé.

JSON/base64 est choisi pour sa simplicité avec une seule image normalisée par appel. Le multipart est aussi documenté, mais inutile ici. Le contrat accepte PNG et JPEG statiques, 16 Mio par image, 280 à 1568 pixels par côté, corps de requête limité à 32 Mio. La normalisation garantit un JPEG sans métadonnées. Les fonctionnalités box et contexte étendu ne sont pas activées.

## Réponse retenue

```json
{
  "model": "jev-1.14.0",
  "answers": {"generated": {"type": "noul", "noul": 0.81}},
  "usage": {"input_tokens": 100, "output_tokens": 12}
}
```

Le client vérifie la présence de l’entrée, son type, la valeur numérique dans [0, 1] et l’identifiant du modèle. Les autres champs sont ignorés. Une réponse partielle, invalide, un statut non 200 ou un timeout rendent Jev indisponible pour le round entier. Le corps d’erreur fournisseur n’est jamais journalisé.

Les modèles documentés sont `jev-1.14.0` et `jev-1.13.0`. Les alias `jev-latest` et `jev-preview` pointent actuellement sur 1.14.0. `GET /v1/models`, authentifié, liste les noms accessibles au compte ; cet endpoint de liste n’a pas été nécessaire : le modèle fixe a ensuite été confirmé par les réponses réelles. La version fixe par défaut rend la configuration explicite.

## Portée de la vérification

Documentation lue et client testé via HTTP local, puis validation réelle le 31 octobre 2026 (voir ci-dessous).

## Mise à jour : validation réelle du 31 octobre 2026

Avec une clé enregistrée dans le fichier `.env` local, non versionné, une sonde sur une image du corpus Sightengine a réussi avec `jev-1.14.0`. Une partie complète exécutée par le script `scripts/smoke_live.py` a ensuite validé les dix réponses réelles sur les cinq rounds, sans indisponibilité. Cela confirme le contrat HTTP retenu et l’accès effectif du compte aux images ; ce n’est ni une certification des images ni une évaluation de précision de Jev.

Une seconde partie réelle de cinq rounds a également été terminée dans le navigateur intégré en viewport mobile, avec dix analyses réussies et révélation finale.
